# Архитектура голосового мессенджера (WebRTC)

## Цель

Описание полной архитектуры голосового мессенджера (в духе Discord), с разделением на роли серверов, их задач и взаимодействия.

---

## Общая схема

```text
[ Electron Client ]
        |
        |  (WebSocket, HTTP)
        v
[ Signaling Server ]
        |
        |  (SDP / ICE)
        v
[ Media Server (SFU) ]
        |
        |  (SRTP / UDP)
        v
[ Other Clients ]

Fallback (если P2P невозможно):

Client → TURN → Client / Media Server
```

---

## Основные компоненты

### 1. Client (Electron)

**Роль:**

- Захват аудио (микрофон)
    
- Кодирование аудио (Opus)
    
- Отправка и получение медиапотоков
    
- UI и управление состоянием
    

**Технологии:**

- Electron
    
- TypeScript
    
- WebRTC (встроен в Chromium)
    
- WebSocket (signaling)
    

**Что клиент НЕ делает:**

- не знает о NAT traversal логике
    
- не управляет другими клиентами
    
- не маршрутизирует чужой трафик
    

---

### 2. Signaling Server (Control Plane)

**Роль:**

- Управление соединениями
    
- Аутентификация пользователей
    
- Комнаты (join / leave)
    
- Обмен WebRTC метаданными
    

**Что передаёт:**

- [[SDP (Session Description Protocol)]]
    
- [[ICE candidates]]
    
- события (mute, leave, kick)
    

**Что НЕ делает:**

- не передаёт аудио
    
- не работает с RTP / UDP
    

**Технологии:**

- Go / Rust / Node.js
    
- WebSocket
    
- JSON
    

**Важно:**

- участвует только на этапе установки соединения
    
- после установления WebRTC — простаивает
    

---

### 3. Media Server (SFU — Selective Forwarding Unit)

**Роль:**

- Принимает медиапотоки от клиентов
    
- Пересылает (fan-out) другим участникам комнаты
    

**Что делает:**

- маршрутизирует RTP пакеты
    
- управляет подписками (кто кого слышит)
    
- ограничивает bitrate
    
- поддерживает simulcast / SVC
    

**Что НЕ делает:**

- не декодирует аудио
    
- не смешивает звук
    
- не улучшает качество
    

**Почему SFU:**

- клиент отправляет только один upload
    
- сервер масштабирует приём
    

**Технологии:**

- LiveKit (Go)
    
- mediasoup (C++ ядро)
    
- Janus
    

---

### 4. STUN Server

**Роль:**

- Помогает клиенту узнать свой публичный IP:PORT
    

**Используется для:**

- попытки прямого P2P соединения
    

**Характеристики:**

- stateless
    
- минимальная нагрузка
    

---

### 5. [[TURN Server]]

**Роль:**

- Ретрансляция медиатрафика, если прямое соединение невозможно
    

**Когда используется:**

- строгий NAT
    
- мобильные сети
    
- корпоративные firewall
    

**Особенности:**

- весь медиатрафик идёт через TURN
    
- дорог по bandwidth
    

**Технологии:**

- coturn (C)
    

---

## Поток подключения (Call Flow)

1. Клиент подключается к Signaling Server
    
2. Проходит аутентификацию
    
3. Входит в комнату
    
4. Получает список участников
    
5. Обменивается SDP через signaling
    
6. ICE пытается установить путь:
    
    - P2P
        
    - через Media Server
        
    - через TURN (fallback)
        
7. Устанавливается SRTP (UDP)
    
8. Signaling больше не участвует
    

---

## Протоколы и кодеки

### Аудио

- Opus (48 kHz, variable bitrate)
    

### Транспорт

- RTP / SRTP — медиа
    
- RTCP — контроль
    
- UDP — основной транспорт
    

### Управление

- WebSocket — signaling
    
- HTTP — REST API
    

---

## Разделение ответственности

|Компонент|Отвечает за|Не отвечает за|
|---|---|---|
|Client|Захват, encode, UI|маршрутизацию|
|Signaling|Управление, комнаты|аудио|
|Media Server|Fan-out RTP|кодирование|
|STUN|IP discovery|трафик|
|TURN|Ретрансляция|бизнес-логику|

|Media Server|Go / C++|
|TURN/STUN|C|

## Ключевые идеи (TL;DR)

- WebRTC — основа всего
    
- Signaling = управление
    
- Media Server = маршрутизация
    
- STUN = узнать адрес
    
- TURN = fallback прокси
